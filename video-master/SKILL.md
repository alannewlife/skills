# Video Master

Use the user's complete written story as the factual and narrative source. A story may be a narration script or a coherent beginning-to-end description. If only a topic is supplied, ask for or help develop the missing story first, and have the user confirm it before this production flow. Preserve the original wording and sequence where practical; propose adaptations visibly, never invent facts. Keep the source immutable in the project.

An approved storyboard image is the visual design to preserve, not merely a subject or style suggestion. Preserve each scene's meaningful objects, proportions, layout, line endpoints, relationships and visual character. Camera close-ups and temporary fades may change what is visible, but each scene must return to an accurate complete view. Never silently omit, replace, rearrange or simplify a meaningful feature; describe unavoidable differences and get explicit acceptance before proceeding. Read [production](references/production.md) for per-scene asset planning and fidelity review.

## Start or resume

1. Check whether a Video Master project is already named. If so read its `project.json`, source, active stage and review notes; resume instead of initializing it again. Otherwise save the supplied complete story as a UTF-8 text or Markdown file and create a new project with the CLI described in [project and review protocol](references/protocol.md).
2. A default company logo is copied into the project; the user can replace or remove it on the style page, or pass `--logo` during initialization. Do not infer or extract a logo from a reference image. Use only the project's current brand asset in generated output; remove the example logo and sample narration from the Remotion template when appropriate.
3. Start the local review server and provide its printed URL. Never submit confirmation, invoke its confirmation endpoint, or edit a confirmation record on the user's behalf. An explicit chat confirmation may be recorded through the documented chat-only protocol in the rare case the page cannot be used. A timeout, page refresh, or silence is not confirmation.
4. The user's confirmation of a particular stage and revision is required before creating deliverables for the next stage. Save notes to the page; if notes request changes, update the artifact and clear the addressed notes using `propose` before asking for confirmation again. Respect revisions and stale downstream stages; never silently reuse stale media.
   Before beginning image or video generation, publish the `processing` state described in the protocol so the affected media frame shows a loading indicator; specify scene IDs for individual storyboard revisions. Clear it on completion, failure, or pause.
5. When asking the user to review in the page, remain active and wait for changes using the protocol's `wait --after-revision` in bounded cycles. In storyboard review, act on the requested scene IDs or the submitted overall request; an ordinary draft save is not by itself a request to regenerate. Process only the submitted comments and preserve other drafts. On confirmation, continue to the next stage. Timeout means keep waiting, not that the user confirmed or work is complete. If the user pauses or the conversation ends, explain that the local page cannot wake an idle Codex chat and the user must resume it in the chat.

## Stages

- **Style:** Present both the verified business line-art style and the paper-collage concept; the latter has no validated video or production template. Allow style overrides and logo replacement. Read the selected `styles/<id>/STYLE.md` and image references. A preview video is an example, never the user's project.
- **Style frame:** Based on the actual story and selected style, produce one original representative image using a suitable available image-generation tool, with its supported reference images when possible. Save under project `assets/` and publish a proposal. If the tool is unavailable, explain and wait; do not relabel a style example as the user's result.
- **Storyboard:** Once the style frame is confirmed, produce a meaningful scene sequence, each with stable unique ID, narrative text, description, and original scene image. Map each scene to source story when feasible, preserve text by default. When designing and drawing each scene image, identify important nodes or relationships that benefit from short, clearly associated explanations and include those labels in the image presented for review. Preserve approved labels in the video; supplement them only when needed for the motion or narration. Before image generation, identify the objects needing independent entrances, focus or motion, their intended layers and the code-drawn elements; preserve original layers, placements and reusable assets when available. Present this plan in each scene's description, including flattened-image reconstruction risks. Do not promise exact separation before demonstrating it. Present and revise until the user confirms.
- **Motion sample:** Implement and show the planned independent layers and their motion, anchored to the approved storyboard; group elements only when they do not need independent movement, or when the user explicitly accepts the specific missing motion after it is disclosed. A pan or zoom of a single flattened image does not demonstrate layered animation. Reconstruct a representative scene and produce narration, a playable sample and an actual encoded-video frame for the page's side-by-side comparison. Disclose differences and missing motion for acceptance. Recommend Xiaomi MiMo, allow a different user-selected voice service, and let the user enter their own Key privately in the page's 配音设置; never ask for a Key in chat or print it. If the chosen service is unavailable or not configured, explain promptly and wait for the user to configure it or explicitly choose a fallback; do not silently substitute a voice. Identify the actual service and voice in the review. For `business-line-art` specifically, read and apply its [narration-driven camera grammar](styles/business-line-art/camera-grammar.md); other styles retain their own motion language. Do not claim missing capabilities or assets are available.
- **Restoration review:** After sample confirmation, produce a playable encoded video clip with narration for every scene and present it beside the confirmed storyboard, together with an actual clip frame, asset/code plan and differences. Review object entrances, explanatory labels, relation lines, narration-driven focus and the return to a complete overview in each clip. Draw each relation line only after its connected objects appear and when the narration introduces that relationship; inspect the actual clip across entrances, focus changes, fades and the overview for orphaned lines or branches. For business-line-art, make the narrated object legibly prominent, then return to the complete overview; a nearly static full-frame zoom is not a substitute for focused explanation. Reuse the approved sample where appropriate. Respond to per-scene requests; require explicit review confirmation for all clips before the final assembly.
- **Final:** Assemble the approved scene clips, adding only transitions or technical changes that preserve the approved scene content. Inspect the actual MP4's encoded overview frames against all confirmed storyboards and clips, as well as audio and transitions, present to the user and iterate. If an approved scene needs substantive changes, return to that scene's review. Deliver final MP4, working source, independent assets where needed, audio and a short record of any limitations. User confirmation of the final video is a separate step.

Schema 1 projects continue their original five-stage workflow until explicitly upgraded; never manufacture past approvals or silently rewrite them. New schema 2 projects require scene clips at restoration. Existing schema 2 projects retain their previous review requirements unless the user requests the clip-based review; when requested, reopen restoration and enable `review_video_required` through `propose`. If the user specifically wants the new gates for a schema 1 project, explain the effect and use the opt-in upgrade command in the protocol. Do not rebuild or modify existing media merely to introduce this flow.

Do not generate later-stage outputs before the corresponding gate. Style selection does not automatically mean approval of the generated style frame. The page records edits and opinions; Codex does the actual generation and must explicitly publish its outputs to the active stage. Never make unsupported claims that the concept style, an image, a voice, or an export is available or validated.
